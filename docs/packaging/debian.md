# Debian packaging

The `.deb` is built by GitHub Actions on **Ubuntu 26.04**, and by
`packaging/build-deb.sh` locally. The script is the same in both places, so a
packaging bug is reproducible without pushing a tag.

The runner is pinned to `ubuntu-26.04` rather than `ubuntu-latest` on purpose:
the crate compiles against GTK 4.18 and libadwaita 1.5, which Ubuntu 24.04 does
not carry, and `ubuntu-latest` only migrates to 26.04 across a two-month window.
Pinning keeps a tagged build reproducible.

## What the package contains

| Path | Purpose |
|------|---------|
| `/usr/bin/mihomo-manifold` | Wrapper. Sets `MIHOMO_MANIFOLD_CORE` and `exec`s the real binary, so it costs no extra process. |
| `/usr/lib/mihomo-manifold/mihomo-manifold` | The GUI. |
| `/usr/lib/mihomo-manifold/mihomo` | The pinned mihomo core. |
| `/usr/share/applications/io.github.cublae.MihomoManifold.desktop` | Menu entry. |
| `/usr/share/icons/hicolor/{scalable,16x16…512x512}/apps/` | App icon, vector plus eight raster sizes. |
| `/usr/share/doc/mihomo-manifold/copyright` | Licence. |

The GUI and the core stay out of `/usr/bin` deliberately: `mihomo-manifold` in
`/usr/bin` has to be the wrapper, or a second `mihomo` on the system would win
the race for the plain name.

`postinst` grants the core `cap_net_admin,cap_net_raw,cap_net_bind_service`, so
TUN works from the first launch and the GUI itself never runs as root. It is
not fatal if that fails: the package is still installed and still works as a
plain proxy, and Settings says so rather than the app failing to start.

`postrm` clears the capabilities on removal, and drops the polkit rule on
`purge` only — the rule is written by the app at the user's request, not by this
package, so `remove` leaves it alone.

## Dependencies

`Depends` is generated by `dpkg-shlibdeps` at build time from the binary's
`DT_NEEDED` entries, with the GTK and libadwaita floors raised to the versions
the crate actually compiles against. It is not a hand-maintained list, and it
should not become one.

Do not replace `dpkg-shlibdeps` with `dpkg -S` lookups. Several of these
libraries are shipped by more than one package — `deepin-wine-runtime` bundles
its own glib, `appimagelauncher` its own libssl — and a plain text match picks
whichever comes first, which puts packages like those in `Depends` for no
reason.

The `t64` suffixed names (`libssl3t64`, `libglib2.0-0t64`) are correct for
Ubuntu 24.04 and newer and wrong for anything older. That is inherent rather
than a bug: GTK 4.18 already rules out those older systems.

## Building locally

```bash
sudo apt-get install --yes --no-install-recommends \
    build-essential dpkg-dev pkg-config \
    libgtk-4-dev libadwaita-1-dev libssl-dev \
    librsvg2-bin

cargo build --release
packaging/build-deb.sh
```

The result lands in `result/mihomo-manifold_<version>_<arch>.deb`. It needs
GTK 4.18 or newer to build, so the host must be Ubuntu 25.10 or newer,
Fedora 42 or newer, or equivalent.

`librsvg2-bin` is what renders the icon. Without it the script falls back to
`python3-cairosvg`; without either it stops. ImageMagick is not an acceptable
substitute — its built-in SVG reader drops everything after the first element,
which silently produces an icon with no foreground.

### Environment variables

| Variable | Default | Purpose |
|----------|---------|---------|
| `MIHOMO_VERSION` | `v1.19.31` | Core version to bundle. Pinned separately from the app's own version: a new core is a security decision, not something a GUI rebuild pulls in silently. |
| `MIHOMO_TAG` | same as `MIHOMO_VERSION` | Release tag the core asset is fetched from, when it differs from the version. |
| `MIHOMO_URL` | derived | Full asset URL, if you need a mirror. |
| `MIHOMO_BIN` | unset | Package an already-downloaded core. Skips the download — useful offline, and what the tests use. |
| `ARCH` | `dpkg --print-architecture` | Target architecture. `amd64` and `arm64` have asset mappings; others stop with a clear error. |
| `OUT` | `result/` | Output directory. |

A core bump is its own commit, so the reason for it is reviewable:

```bash
MIHOMO_VERSION=v1.19.32 packaging/build-deb.sh
```

### Verifying the result

The workflow asserts the package really contains its payload, because a `.deb`
that builds but ships nothing looks identical to a good one until someone
installs it. Worth running the same checks by hand after changing the layout:

```bash
deb=$(ls result/*.deb)
dpkg-deb --info "$deb"
dpkg-deb --contents "$deb" > /tmp/contents.txt
grep -q 'usr/bin/mihomo-manifold' /tmp/contents.txt
grep -q 'usr/lib/mihomo-manifold/mihomo$' /tmp/contents.txt
grep -q 'usr/share/applications/io.github.cublae.MihomoManifold.desktop' /tmp/contents.txt
test "$(grep -c 'hicolor/[0-9]*x[0-9]*/apps/io.github.cublae.MihomoManifold.png' /tmp/contents.txt)" -eq 8
```

Then install it and check the wrapper resolves the bundled core:

```bash
sudo apt install ./result/*.deb
getcap /usr/lib/mihomo-manifold/mihomo     # expect cap_net_admin,cap_net_raw,cap_net_bind_service=ep
mihomo-manifold --print-config > /tmp/c.yaml
```

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| `dpkg-shlibdeps failed` | `dpkg-dev` not installed | `sudo apt install dpkg-dev` |
| `no mihomo asset mapped for '<arch>'` | Architecture not in the `case` in `build-deb.sh` | Add the mapping, or set `MIHOMO_BIN` for a local core |
| Core download fails with a TLS error | The asset CDN is unreachable from your network | `MIHOMO_BIN=/path/to/mihomo packaging/build-deb.sh`. `api.github.com` may still work while release assets do not — they are different hosts |
| `need rsvg-convert … or python3-cairosvg` | Neither renderer installed | `sudo apt install librsvg2-bin` |
| Icon renders as a plain rounded square | ImageMagick used as the renderer | Install `librsvg2-bin`; only the first SVG element survives |
| TUN unavailable after install | `setcap` missing or refused | `sudo apt install libcap2-bin`, then re-run the `setcap` line from `postinst`. Check `getcap /usr/lib/mihomo-manifold/mihomo` |
| Password prompts on every core start | The polkit rule is not installed | Settings → TUN → *Start the core without a password prompt* |
| `Depends` contains a surprising package | A library has several providers and the wrong one was chosen | Should not happen with `dpkg-shlibdeps`; if it does, the tool was bypassed |
